01 // LAB OBJECTIVE

VULNERABILITY CONTEXT

El objetivo consiste en recuperar el contenido de /etc/passwd desde el endpoint encargado de cargar imágenes de producto. A diferencia de los laboratorios anteriores, aquí la aplicación transmite la ruta completa del archivo y verifica que el valor de filename empiece con /var/www/images/.

La debilidad aparece porque comprobar únicamente el inicio de la cadena no garantiza que la ruta final permanezca dentro de ese directorio. Si conservamos el prefijo permitido y después introducimos secuencias de recorrido hacia directorios superiores, el valor supera la comprobación inicial y puede resolverse fuera de la carpeta autorizada.

VULNERABILITY SIGNAL /var/www/images/../../../etc/passwd EXPECTED RESULT // LOCAL FILE CONTENT

02 // RESOLUTION PATH

OFFICIAL 3-STEP FLOW
  1. 01

    Usamos Burp Suite para interceptar e identificar una petición que obtiene una imagen de producto y observamos que filename contiene la ruta completa dentro de /var/www/images/.

  2. 02

    Enviamos la solicitud a Repeater y modificamos filename conservando el prefijo esperado, pero agregando el recorrido necesario hacia /etc/passwd: /var/www/images/../../../etc/passwd.

  3. 03

    Reenviamos la petición y comprobamos que la respuesta contiene las entradas de /etc/passwd, confirmando que la validación del inicio de la ruta puede evadirse.

03 // EVIDENCE RUN

BURP SUITE CAPTURES
STEP_01 // DISCOVERY

Identificamos la ruta completa de la imagen

Desde Proxy → HTTP history localizamos solicitudes GET al endpoint /image. La petición seleccionada utiliza una ruta como filename=/var/www/images/67.jpg, lo que confirma que el servidor recibe la ubicación completa del archivo mediante un parámetro controlable.

STEP_02A // DIRECT PATH TEST

Probamos primero la ruta objetivo de forma directa

En Repeater sustituimos la ruta de la imagen por la ubicación directa del archivo objetivo. El servidor responde con 400 Bad Request y no entrega el contenido esperado, lo que evidencia que la aplicación aplica una validación sobre el valor recibido antes de acceder al sistema de archivos.

STEP_02B-03 // PREFIX BYPASS

Conservamos el prefijo permitido y salimos del directorio

Modificamos filename para que el valor siga comenzando con /var/www/images/, pero añadimos después el recorrido hacia el archivo objetivo. La aplicación acepta la entrada porque supera la comprobación inicial y devuelve HTTP/1.1 200 OK junto con el contenido de /etc/passwd.

04 // TECHNICAL ANALYSIS

WHY THE BYPASS WORKS
01

Validación superficial del prefijo

La aplicación comprueba que la cadena empiece con el directorio permitido, pero no garantiza que la ruta resuelta permanezca dentro de él.

02

Ruta sin canonicalizar

Las secuencias de recorrido incluidas después del prefijo pueden modificar el destino real cuando el sistema de archivos normaliza la ruta.

03

Impacto

Un atacante podría leer archivos locales accesibles para el proceso web aunque la entrada aparentemente comience dentro del directorio autorizado.

04

Mitigación

La aplicación debe canonicalizar la ruta antes de validarla y comprobar que el destino final siga contenido en el directorio permitido; cuando sea posible, conviene trabajar con identificadores o nombres de archivo previamente autorizados.

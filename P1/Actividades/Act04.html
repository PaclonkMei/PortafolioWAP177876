01 // OBJECTIVE BRIEF

MISSION CONTEXT

Implementamos una simulación de phishing dentro de un entorno controlado para comprender cómo una página aparentemente legítima puede inducir a un usuario a proporcionar información. La práctica se centró en la configuración de SET, la creación de un portal ficticio, la recepción local del correo y el análisis de la petición HTTP generada por el formulario.

  • Configurar Social-Engineer Toolkit dentro de Kali Linux.
  • Preparar un correo de laboratorio mediante un servidor SMTP local.
  • Importar una página ficticia en Credential Harvester.
  • Observar el envío de parámetros mediante una petición HTTP POST.
  • Identificar señales de phishing y proponer controles de protección.

02 // SCENARIO

SIMULATED PHISHING CAMPAIGN
INCIDENT_SIM // SESSION EXPIRED

Un portal familiar, una solicitud inesperada.

El escenario representa a un usuario que recibe un mensaje marcado como urgente y es dirigido hacia un portal de autenticación aparentemente institucional. El portal muestra un aviso de sesión expirada y solicita usuario y contraseña para continuar.

Para evitar involucrar servicios o personas reales, toda la simulación permaneció en localhost. El correo fue capturado por Mailpit y el sitio NEXORA fue creado específicamente para esta actividad.

SIMULATION_BOUNDARIES target = lab_user@local.test smtp = 127.0.0.1:1025 web = http://127.0.0.1/ credentials = TEST_DATA_ONLY external_exposure = FALSE

06 // HOW THE HARVESTER WORKS

TECHNICAL ANALYSIS
HTTP_01

Formulario

El portal contiene campos con los nombres username y password. Al presionar el botón, el navegador construye una petición HTTP con los valores introducidos.

HTTP_02

Petición POST

La información viaja hacia el servidor local configurado en 127.0.0.1:80. En el laboratorio no se utilizaron dominios externos ni tráfico publicado hacia Internet.

HTTP_03

Servidor SET

Credential Harvester recibe la petición, identifica los parámetros enviados por el formulario y los muestra en la terminal antes de incorporarlos a su registro.

KEY_DISTINCTION

Capturar ≠ vulnerar

La técnica no descifra ni rompe una contraseña. El valor queda expuesto porque fue proporcionado al formulario y transmitido al servidor que controla la página.

07 // PHISHING INDICATORS

DETECTION MATRIX
01
DOMINIO O URL INESPERADA

El destino no coincide con el sitio que el usuario esperaba visitar. La apariencia visual no demuestra propiedad del dominio.

02
SOLICITUD INESPERADA DE CREDENCIALES

Un mensaje de sesión expirada obliga a preguntarse por qué se requiere autenticación nuevamente y desde qué origen.

03
URGENCIA O PRESIÓN

Mensajes marcados como urgentes reducen el tiempo que el usuario dedica a verificar el contexto antes de actuar.

04
REMITENTE / CONTEXTO INCONSISTENTE

El nombre visible del remitente puede ser persuasivo, pero debe contrastarse con la dirección real y el canal habitual.

05
SEÑALES TÉCNICAS NO CONCLUYENTES

Diseño, logotipo e incluso HTTPS pueden imitarse. La verificación debe centrarse en origen, dominio y contexto, no solo en apariencia.

08 // SECURITY CONTROLS

DEFENSIVE COUNTERMEASURES
MFA

Autenticación multifactor / passkeys

Reduce el impacto de una contraseña capturada. Su alcance depende del método: algunas formas de MFA todavía pueden ser objeto de phishing.

PWM

Gestores de contraseñas

El autocompletado ligado al dominio puede alertar cuando el sitio no coincide. No impide que una persona escriba los datos manualmente.

MAIL

Filtrado de correo y URLs

Los gateways y analizadores de enlaces pueden bloquear campañas conocidas, aunque no garantizan detectar mensajes nuevos o muy dirigidos.

DMARC

SPF, DKIM y DMARC

Ayudan a reducir la suplantación directa de dominios protegidos, pero no eliminan el riesgo de dominios visualmente similares.

USER

Concientización y verificación

Promueve verificar solicitudes sensibles mediante canales conocidos y acceder a servicios desde marcadores o direcciones escritas manualmente.

09 // CONCLUSION

LESSONS LEARNED
04

La actividad permitió comprobar que la efectividad de una campaña de phishing no depende necesariamente de explotar una vulnerabilidad técnica. Una interfaz convincente, un mensaje con sentido de urgencia y una solicitud de autenticación pueden ser suficientes para provocar que la propia víctima entregue información.

Al observar el proceso dentro de localhost pudimos diferenciar la captura de parámetros de una vulneración de contraseña y reconocer que la defensa requiere combinar controles técnicos con hábitos de verificación por parte del usuario. Mantener toda la prueba dentro de un entorno ficticio permitió estudiar el riesgo sin involucrar sistemas, dominios ni credenciales reales.
